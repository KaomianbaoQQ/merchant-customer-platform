# 客服整合 + 物流权限校验（规划）

## Context（为什么做）
现状客户前端有 3 个独立客服：`商品咨询`(#1 consult，机器答 Dify)、`联系商家`(#2 merchant，等商家人工回)、`售后`(#3 after，订单/退换/物流)。

用户要求：
1. **去掉独立机器客服，与商家客服整合为一个智能客服**；售后保留独立。整合后客户发消息一律由 Dify「商品咨询」工作流基于商品信息知识库**自动回答，不依赖商家**；当客户说出「人工/转人工/真人客服…」**满 3 次**才把该会话标记为「需人工」并附完整对话，商家在商户后台「顾客消息」看到高亮/角标并可回复。
2. **用户所有聊天与回答都作为上下文传给 Dify**，提升意图判断与回答质量。
3. **物流查询加物权校验**：除 admin 外禁止查询别人的物流（客户 /api/logistics/*、商家 /api/merchant/logistics 都要）。
4. **只整理本次新改动代码，分门别类；不动现有模块物理位置，确保能跑。**

已确认决策：售后保留；复用现有「商品咨询」Dify 工作流；人工×3 用 chat.json 会话标记 + 商户后台高亮记录；文件整理仅限新改动。

## 改动清单

### Step 1 — 公共/store.py（会话存储扩展）
- `append_message(merchant_id, user_id, user_name, role, text, merchant_name="", suppress_unread=False)`：
  - 允许 `role == "bot"`；bot 消息 dict 加 `"is_bot": True`（便于前端区分气泡、商家端不把它当自己/顾客消息）。
  - `suppress_unread=True` 时不递增 `unread_merchant`（普通知识库问答不打扰商家）。默认行为不变。
- 新增 `mark_needs_human(merchant_id, user_id)`：置 `thread["needs_human"]=True`、`human_since=now`，并递增一次 `unread_merchant`（给商家发“通知”）。
- `get_thread`：返回的 thread 自动含 `needs_human`（新增字段，旧数据 `setdefault`）。
- `list_conversations`：摘要 dict 增加 `needs_human`（`bool`），供商户后台高亮。

### Step 2 — 客服/workflow.py（上下文传输，向后兼容）
- `build_product_prompt(message, product=None, conversation_history=None)`：商品信息后追加「对话上下文：」块，取最近 ~10 条 `[{role, text}]`（把现有 `message` 也保留其中）。
- `ask_product_service(user_input, product=None, user_id="web", conversation_history=None)`：新增可选参数并拼入。**不传即保持原行为**（`/api/consult` 不受影响）。
- 说明：Dify 工作流入参仍是 `user_input`（历史拼入 prompt，不新增工作流入参）。

### Step 3 — 新增 客服/auto_reply_service.py（合并客服编排，供 chat.py 复用）
把单条消息的完整处理放这里，逻辑集中、易测：
- `HUMAN_RE` 判定（复用前端正则：人工/真人/转人工/人工客服/人工服务/找客服/要客服/客服在吗/真人客服）。
- `_count_human_hits(thread)`：统计该会话 `role=="user"` 消息中命中「人工」的次数（可只在最近若干条/按连续命中计数，采用“累计命中达 3”最贴合需求）。
- `handle_chat_message(text, product, user, merchant_id, merchant_name)`：
  1. 存用户消息（若会话已 `needs_human` → 正常递增 `unread_merchant`；否则 `suppress_unread=True`）。
  2. 若命中「人工」≥3 且未 `needs_human`：`append_message(bot, "已为您转接人工客服，商家会尽快回复…")` → `mark_needs_human` → 返回 `{needs_human: True, bot: "已为您转接…"}`。
  3. 否则：取 thread 最近对话作为 history，调 `ask_product_service(text, product, user_id, history)`，把 `reply` 用 `append_message(role="bot", suppress_unread=True)` 落盘，返回 `{bot: reply, bot_message_id, needs_human: False}`。
  4. Dify 失败时返回兜底话术（同 workflow 现有风格）。

### Step 4 — 后端/routes/chat.py（入口改为自动回答）
- `POST /api/chat`：改为调用 `auto_reply_service.handle_chat_message(...)`，返回体在保留原 `message` 基础上新增 `bot` / `bot_message_id` / `needs_human`。
- `GET /api/chat`：保持不变（返回会话 messages，含 bot 气泡）。

### Step 5 — 后端/routes/logistics.py（客户物流物权）
- 两个接口都读取并 `resolve_user({id: user_id, name: user_name})` 校验身份；未带身份/校验失败 → 401。
- `GET /api/logistics?user_id=&user_name=`：非 admin 强制只能用 `resolve_user` 返回的本人 id 查询（传别人 → 403 或直接按本人忽略）。
- `GET /api/logistics/<waybill>`：取 row 后，非 admin 且 `row.user_id != user.id` → 403。
- 前端 `doTrack` 需带 `?user_id=&user_name=`，未登录先提示登录。

### Step 6 — 后端/routes/merchant.py（商家物流物权 + 会话高亮字段）
- `api_merchant_logistics`（GET /api/merchant/logistics）：取到 row 后校验该物流关联 `order_ids` 订单的商品是否至少一单属于当前商户 `m["id"]`；不属于 → 403。可复用 `store.list_products(owner_id=m["id"])` 的 id 集合 + `售后/order.py get_orders_by_user`/按字段比对商品归属。
- `api_merchant_chats` / `chats/thread`：`list_conversations`/`get_thread` 已带回 `needs_human`，原样透出即可，无逻辑改动。

### Step 7 — 前端/客户前端.html（客服整合 + 物流传身份）
- 合并 `consult` 与 `merchant` 为单模式（表头文案改为「在线客服 / 联系商家」），去掉 `merchant` 切换 tab；保留 `after` tab。
- `csSend` 统一 `POST /api/chat`，body 带 `message / product / user / merchant_id / merchant_name`。
- 响应处理：`data.bot` → `csPush('bot', ...)`；`data.needs_human` → `csPush('sys','已为您转接人工客服…')` 并启动 `startMerchantPolling()` 展示商家回复。
- 删除前端 `humanHits` 计数与 `autoConnectMerchant`（改由后端判定）。
- `loadMerchantMessages` 对 `role==="bot"` 渲染为 bot 气泡。
- `doTrack`（L~1765）：请求加 `?user_id=&user_name=`；未登录提示先登录。

### Step 8 — 商户界面 index.html（商家后台高亮 + bot 渲染）
- `renderConversations`：`needs_human` 会话加高亮 class + “待人工”角标。
- 消息渲染：`role==="bot"` 显示为 bot 气泡（样式可复用顾客侧辅助色）。

### Step 9 — Dify「商品咨询」工作流核对（调用知识库的工作流更新）
- 用浏览器进 Dify 核对「商品咨询」工作流：知识检索节点是否指向「商品信息知识库」（现已是 high_quality + qwen3-embedding），若指向旧/缺失则更新并**重新发布**工作流，确保自动回答能命中真实商品。

### Step 10 — 文件整理（仅新改动）
- 合并客服编排放 `客服/auto_reply_service.py`（chat.py import 之，`客服/` 为客服逻辑目录）。
- 商品描述文件保留 `商品咨询/`；知识库同步仍属 `公共/knowledge.py`（共享基础设施，不动）。
- 后台运行服务启动方式不变（`python main.py`）。

## 风险 / 兼容
- `append_message` 角色/未读扩展须保持旧行为：普通顾客消息仍计商家未读的旧模式，改成 `suppress_unread` 后，普通问答不再打扰商家、仅在「人工×3」时通知，符合需求，但需在商户后台确认“正常问答不出现未读、转人工后出现未读”符合预期。
- bot 消息勿计入 `unread_merchant`，避免商家端把 bot 回答当顾客留言。
- 前端 `merchantSeen` 需并入 `bot_message_id`，避免轮询重复渲染。
- 不改现有 `/api/consult`、售后、订单、商家发货流程；Dify 工作流入参仍为 `user_input`（历史拼 prompt）。

## 验证（端到端）
1. 重启后端（`python main.py`，后台）。
2. 用商户已有商品（如「珠颈斑鸠」）或在 /api/merchant 创建/修改商品触发知识库同步（文件落盘 + Dify 文档 completed）。
3. 客户前端发普通咨询「这款有参数吗」→ 界面出现 bot 回答，`商户界面/chat.json` 出现 bot 消息，且商家端该会话未读不增加。
4. 连发 3 条含「人工」→ 接口 `needs_human=true`，bot 提示已转人工；商家后台 `/api/merchant/chats` 该会话 `needs_human=true` 且高亮角标，可回复。
5. 物流越权：注册 A、B 两账号各自下单发货；A 带自己身份查 B 的运单号 → 403；B 查自己 → 200；admin 皆可；商家查非自家运单 → 403。
6. 回归：`/api/consult`、`/api/orders`、售后、商家发货/物流仍正常。
